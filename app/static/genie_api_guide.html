Genie API Gateway 외부 연계 API 명세서

본 가이드는 외부 시스템(CRM, ERP, 웹사이트, 모바일 앱 등) 개발자가 Databricks Genie Agent API Gateway를 통해 자연어 대화 기반 데이터 분석 및 SQL 질의 기능을 통합할 수 있도록 안내합니다.

💡
Databricks Genie Conversation API 호환
외부 시스템은 Databricks Conversation API와 동일한 Path, Body 및 응답 형식을 사용하고, Gateway 인터페이스 정의인 X-API-Key, source_system, user_id만 추가합니다.
!
Gateway 적용 범위
Gateway는 등록된 시스템과 Genie Space의 연결을 확인하고, 기존 대화 요청에서는 최초 요청과 동일한 source_system·user_id의 소유권을 검증합니다. GET /conversations는 Databricks 전체 목록이 아니라 현재 외부 사용자에게 귀속된 대화만 반환합니다.

기본 연동 모델: Agent Mode SSE

운영 연동의 기본 흐름은 Agent Mode SSE입니다. POST /agents/{agent_id}/responses 연결을 유지하면서 response.created, 중간 Output Item, response.completed 또는 response.failed 이벤트를 순서대로 처리합니다. Chat Mode의 비동기 Polling API는 호환·보조 용도로 제공합니다.

인증 및 공통 파라미터

모든 API 요청 시 API Gateway 인증을 위한 HTTP Header와 호출 주체를 식별하는 Query Parameters가 필수적입니다.

💡
운영 환경은 Databricks Apps 전환을 기준으로 합니다.
외부 시스템은 사전에 등록된 외부 시스템용 Databricks Service Principal(DBX SP)의 OAuth Client ID와 Secret으로 access token을 발급받아야 합니다. 운영 API 요청에는 해당 토큰의 Authorization: Bearer 헤더와 Gateway가 발급한 X-API-Key를 함께 전달합니다.

1. Request Headers

Header Name Type Required Description
Authorization string Required (Apps 운영) 외부 시스템용 DBX SP의 OAuth access token. 형식: Bearer <access_token>
X-API-Key string Required 발급받은 Gateway API Secret Key (예: gw_live_abc123...)
Content-Type string Required (POST) application/json

2. 필수 Query Parameters

모든 REST 엔드포인트 URL 뒤에 아래 두 쿼리 파라미터를 반드시 포함해야 합니다.

Query Parameter Type Required Description
source_system string Required 호출하는 외부 시스템의 영문 코드명. (예: CRM, EXGPT, ERP_PORTAL)
user_id string Required 외부 시스템 내부의 최종 요청 사용자 식별자 (예: user123@company.com)

source_system과 user_id는 Databricks Query Parameter로 전달하지 않습니다. 다만 Chat 대화 시작·후속 질문과 Agent API의 input_text에는 Gateway가 [user_id: <value>]를 내부 질의 컨텍스트로 자동 삽입합니다. 이 표식은 외부 API 응답·SSE·Gateway 대화 이력에서 제거됩니다. 그 외 Databricks Query Parameter는 그대로 전달됩니다.

3. Databricks Apps OAuth 발급 및 갱신

운영 환경의 Databricks Apps 호출에는 Authorization: Bearer <OAuth access token>과 X-API-Key가 모두 필요합니다. Apps 프록시가 OAuth 토큰과 App CAN USE 권한을 먼저 검증하고, Gateway가 X-API-Key와 source_system을 추가 검증합니다.

💡
두 Service Principal의 역할
외부 시스템은 자신에게 발급된 외부 시스템용 DBX SP의 Client ID와 OAuth Secret으로 Apps 진입용 토큰을 발급합니다. Apps 내부에서 Genie를 호출하는 App SP 자격증명은 Databricks가 앱 런타임에 주입하며 외부 시스템에 제공하지 않습니다.

사전 조건

  1. 외부 시스템용 Databricks Service Principal 생성
  2. 해당 SP의 Application ID(Client ID)와 OAuth Secret 발급
  3. 대상 Databricks App에 해당 SP의 CAN USE 권한 부여
  4. Client ID와 Secret을 외부 시스템의 승인된 Secret 저장소에 보관
1

캐시 확인

저장된 access token이 만료 5분 이상 남았으면 그대로 사용합니다.

2

OAuth 발급

Workspace의 /oidc/v1/token에 Client ID·Secret으로 요청합니다.

3

만료시간 저장

access_token과 expires_in 기준 만료시각을 함께 캐시합니다.

4

Apps 호출

App URL에 Bearer token과 X-API-Key를 함께 전송합니다.

i
호스트 구분
토큰은 https://<workspace-host>/oidc/v1/token에서 발급하고, 실제 Gateway API는 https://<app-name>-...databricksapps.com으로 호출합니다.
curl -X POST "https://<workspace-host>/oidc/v1/token" \
  -u "<CUBE_SP_CLIENT_ID>:<CUBE_SP_CLIENT_SECRET>" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "scope=all-apis"

# 응답
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 3600
}
// 실제 구현에서는 동시 요청이 한 번만 갱신하도록 lock/single-flight 적용
OAuthToken token = tokenCache.get();
if (token == null || token.expiresAt().isBefore(Instant.now().plusSeconds(300))) {
    token = webClient.post()
        .uri("https://<workspace-host>/oidc/v1/token")
        .headers(h -> h.setBasicAuth(clientId, clientSecret))
        .contentType(MediaType.APPLICATION_FORM_URLENCODED)
        .body(BodyInserters.fromFormData("grant_type", "client_credentials")
            .with("scope", "all-apis"))
        .retrieve()
        .bodyToMono(OAuthTokenResponse.class)
        .map(r -> OAuthToken.of(r.accessToken(), Instant.now().plusSeconds(r.expiresIn())))
        .block();
    tokenCache.set(token);
}

// client_credentials 방식에는 refresh_token이 없음:
// 만료 5분 전 Token Endpoint를 다시 호출하여 새 access_token 발급
curl -N -X POST "https://<app-name>-<app-id>.<region>.databricksapps.com/api/2.0/genie/agents/<agent_id>/responses?source_system=CUBE&user_id=1234" \
  -H "Authorization: Bearer <OAUTH_ACCESS_TOKEN>" \
  -H "X-API-Key: <CUBE_X_API_KEY>" \
  -H "Accept: text/event-stream" \
  -H "Content-Type: application/json" \
  -d '{"input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"질문"}]}]}'
!
갱신 규칙
M2M access token의 유효기간은 응답의 expires_in을 기준으로 관리합니다(일반적으로 3600초). 토큰을 요청마다 발급하지 말고 캐시한 뒤 만료 5분 전에 재발급합니다. Apps API가 401을 반환하면 캐시를 폐기하고 새 토큰으로 한 번만 재시도합니다. Client Secret과 access token을 로그에 기록하지 않습니다.

핵심 연동 워크플로우 (Agent Mode SSE)

외부 시스템 개발자가 구현할 기본 대화·화면 렌더링 흐름입니다.

1

인증 준비

OAuth token을 준비하고 Bearer token, X-API-Key, 시스템·사용자 값을 요청에 설정합니다.

2

SSE 요청 시작

POST /agents/{agent_id}/responses를 호출하고 HTTP 스트리밍 연결을 유지합니다.

3

이벤트 렌더링

response.created의 ID를 저장하고 Output Item을 답변·진행상태·결과표로 표시합니다.

4

완료·후속질문·취소

완료 시 연결을 닫고, 후속 요청에는 conversation_id를 넣습니다. 중단 시 Cancel API를 먼저 호출합니다.

⚠️
SSE 종료 조건
response.completed 또는 response.failed 수신 시 연결을 종료합니다. 사용자 중단은 SSE 연결만 닫지 말고 Cancel API 호출 후 연결을 닫습니다.

Chat Mode · 메시지 상태 및 결과 조회 GET /api/2.0/genie/spaces/{space_id}/conversations/{conversation_id}/messages/{message_id}

특정 메시지의 진행 상태 및 최종 응답 내용(텍스트, SQL Attachment 등)을 조회합니다. Polling 루프의 대상 엔드포인트입니다.

Status Enum 설명

진행 상태 SUBMITTED, ASKING_AI, PENDING_WAREHOUSE, FILTERING_CONTEXT, EXECUTING_QUERY 등은 진행 중이므로 계속 Polling합니다. Databricks가 상태를 추가할 수 있으므로 완료·실패 상태 외에는 진행 중으로 처리합니다.

Chat Mode Attachment 유형과 처리 방법

메시지 상태가 COMPLETED이면 attachments[]를 순회합니다. 각 원소는 아래 네 가지 응답 유형 중 하나이며, 존재하는 필드를 기준으로 구분합니다.

유형판별 필드주요 내용외부 화면 처리
Textattachment.textcontent, purpose최종 답변 또는 확인 질문을 텍스트로 표시
Queryattachment.querytitle, description, query, query_result_metadata생성 SQL을 표시하고 attachment_id로 결과 조회
Suggested Questionsattachment.suggested_questionsquestions[]후속 질문 버튼 목록으로 표시
Visualizationattachment.viztitle, query_attachment_id조건부 결과입니다. 존재할 때만 연결된 Query 결과를 차트로 표시하거나 시각화 이미지 조회
i
Text의 purpose도 확인합니다.
TEXT_ATTACHMENT_PURPOSE_ANSWER는 최종 답변이고, FOLLOW_UP_QUESTION은 사용자의 추가 확인이 필요한 질문입니다. query_result는 Deprecated 필드이므로 Query의 query_result_metadata와 Query Result 조회 API를 사용합니다.
!
Attachment 배열의 유형과 순서를 고정값으로 가정하지 않습니다.
Text·Query·Suggested Questions·Visualization이 혼합되거나 일부만 올 수 있습니다. enable_visualization=true도 시각화 생성 보장이 아니므로 필드 존재 여부로 렌더링하고, Visualization이 없으면 텍스트와 표 결과만 표시합니다.

JavaScript 유형 판별 예시

function getAttachmentType(attachment) {
  if (attachment.text) return "text";
  if (attachment.query) return "query";
  if (attachment.suggested_questions) return "suggested_questions";
  if (attachment.viz) return "visualization";
  return "unknown";
}

for (const attachment of message.attachments ?? []) {
  const type = getAttachmentType(attachment);

  if (type === "text") {
    renderText(attachment.text.content, attachment.text.purpose);
  } else if (type === "query") {
    fetchQueryResult(attachment.attachment_id);
  } else if (type === "suggested_questions") {
    renderQuestionButtons(attachment.suggested_questions.questions);
  } else if (type === "visualization") {
    renderVisualization(attachment);
  }
}
Chat Mode · SQL 쿼리 결과 조회 GET /api/2.0/genie/spaces/{space_id}/conversations/{conversation_id}/messages/{message_id}/attachments/{attachment_id}/query-result

조회 결과가 0건이면 HTTP 성공과 함께 result가 빈 object이거나 data_array가 없을 수 있습니다. 이를 오류로 간주하지 말고 “조회 결과 없음”으로 표시합니다.

Path Parameters

attachment_id string COMPLETED 메시지의 attachments[].attachment_id 값

  -H "Authorization: Bearer <OAUTH_ACCESS_TOKEN>" \
  -H "X-API-Key: gw_live_secret_key_123"
{
  "statement_response": {

    "result": {
      "data_array": [

Supervisor 통합 API
POST /api/v1/agents/{agent_id}/responses는 정규화 SSE를 반환합니다. 요청 Body는 input, 선택적인 conversation_id, client_message_id, long_task, metadata를 사용하며, 재시도 요청에는 같은 Idempotency-Key Header 사용을 권장합니다.

Supervisor의 원본 Item·Streaming·MCP Approval 구조는 OpenAI Responses API의 개념을 참고합니다. 다만 CUBE가 구현해야 하는 외부 인터페이스는 OpenAI 원본 이벤트가 아니라 이 문서의 Genie Gateway 정규화 API 명세와 SSE 이벤트입니다.
curl -N -X POST "https://gateway.example.com/api/v1/agents/HEALTHCARE_SUPERVISOR/responses?source_system=CUBE&user_id=user-10001" \
  -H "Authorization: Bearer <OAUTH_ACCESS_TOKEN>" \
  -H "X-API-Key: <api-key>" \
  -H "Idempotency-Key: cube-message-10001" \
  -H "Content-Type: application/json" \
  -d '{"input":"이번 달 주요 지표를 분석해줘","long_task":false}'
기능Method·Path
Run 상태GET /api/v1/agents/{agent_id}/runs/{run_id}
Run 중단POST /api/v1/agents/{agent_id}/runs/{run_id}/cancel

SSE는 run.started, 중간 message.*·tool.*, 마지막 run.completed·run.failed·run.cancelled·run.timed_out 중 하나를 전달합니다. SSE 연결 종료만으로 Run이 중단되지는 않으므로 사용자 중단은 반드시 Run 중단 API를 호출해야 합니다.

!
Gateway가 공개 SSE heartbeat를 임의 생성하지 않습니다.
Databricks가 전달하는 공식 이벤트와 Gateway에 저장된 Run 이벤트만 제공합니다. 이벤트가 없는 구간에는 : ping 같은 주기적 comment가 오지 않을 수 있으므로, CUBE는 HTTP 응답이 조용하다는 이유만으로 실패로 판정하지 말고 Run 상태 조회와 문서화된 timeout을 기준으로 처리해야 합니다.

long_task=true인 Supervisor가 continuation checkpoint를 반환하면 Gateway가 같은 Run 안에서 자동 후속 호출합니다. 클라이언트는 내부 continuation ID 대신 run.continuing 이벤트의 continue_count와 step만 처리하면 됩니다.

Web Search 실행 전에는 approval.required가 전달되고 현재 SSE가 종료됩니다. 클라이언트는 approval_id, name, arguments를 사용자에게 보여준 뒤 승인/거절 API를 호출하고, 그 응답 SSE를 계속 읽어야 합니다. Gateway는 WAITING_APPROVAL 상태와 승인 이력을 DB에 저장하며 같은 run_id를 재개합니다.

SSE 재접속 시 최초 요청과 동일한 Idempotency-Key를 사용하고 마지막으로 처리한 SSE id를 Last-Event-ID Header에 전달합니다. Gateway는 같은 Run을 재사용하고 해당 Event 다음 순번부터 저장 Event를 재생합니다.

Gateway 운영자는 /custom/supervisor-chat에서 등록된 Supervisor를 선택하여 SSE 출력, long task continuation과 사용자 중단을 직접 검증할 수 있습니다. 이 화면의 BFF 경로는 외부 OpenAPI 명세에 노출되지 않습니다.

완료 Item 조회: 최종 메시지, 도구 결과, 표·출처 등은 GET /api/v1/agents/{agent_id}/conversations/{conversation_id}/items로 복원합니다. CUBE는 item_type과 content를 기준으로 텍스트·표·차트 컴포넌트를 분리해 렌더링해야 하며, Gateway가 PNG 이미지를 만들어 준다고 가정하지 않습니다.

i
대화 목록은 모드별로 별도 구성합니다.
Chat Mode는 Space Conversation 목록, Agent Mode는 Gateway 소유권 목록과 Agent /items, Supervisor는 Gateway Supervisor Conversation/Run 이력을 각각 사용합니다. CUBE가 한 화면에 통합 목록을 제공하려면 세 목록을 자체 화면 모델로 합치되, 각 항목에 모드와 agent_id를 보관하여 상세 조회 API를 구분해야 합니다.

API Reference: Agent Mode (SSE Streaming)

단일 HTTP 스트리밍(Server-Sent Events) 연결을 통해 Agent 실행 이벤트를 제공하는 엔드포인트입니다. Databricks가 텍스트 delta를 보내는 경우에는 점진적으로 표시할 수 있지만, 완료된 Output Item만 보내는 실행에서는 Item 완료 시점에 한 번에 표시됩니다.

1

SSE 요청 시작

POST /responses를 호출하고 HTTP 응답 연결을 유지합니다.

2

응답 ID 저장

response.created 이벤트의 conversation_id와 response_id를 저장합니다.

3

이벤트 전달

수신한 data: 이벤트를 순서대로 파싱하여 채팅 화면에 전달합니다.

4

완료 또는 취소

완료 이벤트까지 수신하거나, 사용자 중단 시 저장한 ID로 Cancel API를 호출합니다.

!
SSE 연결 종료와 응답 취소는 다릅니다.
클라이언트가 HTTP 연결만 닫으면 화면 수신은 멈추지만 Databricks 작업 취소는 보장되지 않습니다. 중단 버튼은 먼저 Cancel API를 호출하고, 그 후 SSE 연결을 닫도록 구현합니다.
Agent Mode · SSE 응답 생성 POST /api/2.0/genie/agents/{agent_id}/responses

Server-Sent Events(SSE) 방식으로 Databricks가 제공하는 응답·진행 상태 이벤트를 수신합니다. 각 이벤트의 sequence_number 순서를 지키고, response.completed 또는 response.failed를 받으면 스트림 처리를 종료합니다. Gateway는 별도의 heartbeat나 가상 token delta를 삽입하지 않습니다.

브라우저 기본 EventSource는 POST Body와 X-API-Key 헤더를 보내기 어렵기 때문에 사용하지 않습니다. 외부 시스템 백엔드에서는 HTTP 스트리밍 클라이언트를, 브라우저에서는 fetch() 스트림 또는 자체 백엔드 중계를 사용합니다.

JSON Request Body

input array[object] Required 단일 User 메시지 구조 배열. [{ "type": "message", "role": "user", "content": [{ "type": "input_text", "text": "질문" }] }]
conversation_id string Optional 기존 대화 이어나갈 시 전달
stream boolean Optional Databricks Agent streaming 선택값. SSE 응답 형식을 사용하더라도 upstream이 token delta 대신 완료 Item만 보낼 수 있습니다.
enable_viz boolean Optional 시각화 생성을 요청하는 조건부 힌트입니다. 결과 데이터·질문·Agent 판단에 따라 시각화가 생성되지 않을 수 있으며 PNG 반환을 보장하지 않습니다.
i

Agent Mode · 진행 중 응답 취소 POST /api/2.0/genie/agents/{agent_id}/conversations/{conversation_id}/responses/{response_id}/cancel

진행 중인 Agent 응답을 취소합니다. conversation_id는 SSE의 response.conversation_id, response_id는 response.id에서 가져옵니다. 취소는 즉시 강제 종료가 아니라 다음 Agent 처리 경계에서 반영될 수 있습니다.

Gateway는 요청의 source_system·user_id와 등록된 Conversation 소유권을 확인한 후 Databricks 취소 API를 호출합니다.

외부 시스템 구현 순서

  1. SSE 요청을 시작하고 response.created 이벤트를 기다립니다.
  2. 이벤트 JSON의 response.conversation_id와 response.id를 사용자 요청 상태에 저장합니다.
  3. 사용자가 중단을 누르면 저장한 두 ID와 최초 요청의 동일한 source_system·user_id로 Cancel API를 호출합니다.
  4. Cancel 응답을 받은 뒤 SSE 수신 연결을 닫고 화면 상태를 ‘취소 요청’으로 변경합니다.
curl -X POST "https://gateway.example.com/api/2.0/genie/agents/01ef_agent_55/conversations/01ef_conv_77/responses/01ef_response_88/cancel?source_system=CUBE&user_id=1234" \
  -H "Authorization: Bearer <OAUTH_ACCESS_TOKEN>" \
  -H "X-API-Key: gw_example_key"

오류 응답

Gateway 자체 오류와 Databricks가 반환한 JSON 오류는 동일한 공통 형태로 전달됩니다. 모든 응답의 x-request-id를 장애 문의 시 함께 전달합니다.

{
  "error_code": "PERMISSION_DENIED",
  "message": "..."
}
HTTP대표 원인
400필수 Parameter 또는 Body 형식 오류
401X-API-Key 누락 또는 유효하지 않은 키
403X-API-Key 소속 시스템과 source_system 불일치 또는 Databricks 권한 부족
404해당 시스템에 등록되지 않은 Genie Space/Agent
409신규 Conversation 소유권이 기존 등록 정보와 충돌
429Databricks 요청 제한
502/503/504Databricks 인증·연결 또는 일시적 Upstream 장애
