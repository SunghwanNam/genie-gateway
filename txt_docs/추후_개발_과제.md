# Genie API Gateway 추후 개발 과제

> 목적: 현재 X-API-Key 방식에서 시작하여, 외부 시스템 SSO 및 사용자별 Unity Catalog 권한까지 단계적으로 확장하기 위한 개발 Backlog

## 단계별 목표

| 단계 | 사용자 식별 | Genie 질의 컨텍스트 | Databricks 실행 주체 | 보안 경계 |
|---|---|---|---|---|
| 1. 초기 적용 | `user_id` Query Parameter | Gateway가 `content`에 삽입 | Gateway SP | X-API-Key, 대화 소유권, UC의 Gateway SP 권한 |
| 2. 회사 SSO 연동 | 외부 시스템 OAuth Token Claim | 검증된 사용자 ID를 Gateway가 삽입 | Gateway SP | Token 검증 + 기존 보안 경계 |
| 3. 사용자별 UC 권한 | Databricks 사용자 Identity | 사용자 신원과 질의 연계 | 사용자 OAuth/OBO | UC가 실제 사용자 기준으로 행·열 권한 적용 |

## Task 1. Gateway `user_id` 컨텍스트 삽입 - 완료

**목표**  
외부 시스템이 보낸 `user_id`를 Gateway가 Genie 질문 앞에 자동 삽입.

```text
[user_id: 1234]
내가 작성한 지식 게시글을 찾아줘
```

**변경 대상**

- Conversation 시작·후속 질문의 `content` 전처리
- Agent API 사용 시 `input_text` 전처리
- Chat·Agent API 적용 지점과 단위 테스트
- API 명세서·구현 명세서·배포 환경 예시 동기화

**완료 기준**

- 외부 요청 Body는 기존처럼 순수 질문만 포함
- X-API-Key로 인증된 CUBE 요청의 `user_id`만 Genie 컨텍스트로 사용
- Gateway 로그와 외부 응답에서 불필요한 개인정보 노출 방지
- JSON/SSE 외부 응답과 DB Message 이력에서 삽입 표식 제거
- 기존 대화 소유권 검증 유지

## Task 2. Genie Space 질의 규칙 설정

**사용자 매핑 경로**

```text
CUBE co_channelmembers.USERID
        ↓
CUBE fr_user.USER_ID
        ↓
CUBE fr_user.EMP_NO
        ↓
KNWBLG account.EMP_NO
        ↓
KNWBLG article.EMPNO_REGIST
```

**Instruction 핵심 규칙**

1. 질문 첫 줄의 `[user_id: 값]`을 현재 외부 사용자 ID로 해석
2. "내가", "내 글", "내 대화"와 같은 질의는 반드시 해당 ID로 필터링
3. 지식블로그 작성자 조회는 `fr_user.USER_ID → fr_user.EMP_NO → article.EMPNO_REGIST` 경로 사용
4. ID 매핑에 실패하면 임의의 사용자로 조회하지 않고 매핑 불가로 응답
5. 현재 ID 이외의 개인정보는 답변에 출력하지 않음

**사전 확인**

- `user_id`가 CUBE `fr_user.USER_ID`와 동일한 값인지 확정
- SSO 연동 전까지 `user_id`의 신원 정확성은 인증된 CUBE 서버가 보장한다는 전제 적용
- `EMP_NO` 형식·자릿수·0 padding 처리가 두 도메인에서 동일한지 검증
- Genie에는 원천 테이블 전체보다 필요 컬럼만 포함한 View 노출 권장

## Task 3. 외부 시스템 SSO/OAuth 연동

**개발 항목**

- OAuth Issuer, Audience, JWKS Endpoint, 사용자 Claim 정의
- `Authorization: Bearer` Token의 서명·만료·Issuer·Audience 검증
- Token Claim에서 사용자 ID 추출
- Query Parameter `user_id` 의존 제거
- JWKS 캐시, Key Rotation, 인증 실패 응답, 감사 로그 구현
- 개발·전환 기간의 기존 X-API-Key 인증과 병행 정책 결정

**CUBE 요청 인터페이스 예정안**

```http
Authorization: Bearer <CUBE_USER_ACCESS_TOKEN>
X-API-Key: <CUBE_GATEWAY_API_KEY>
```

`source_system=CUBE`와 질문 `content`는 기존처럼 전달하며, `user_id`는 Token Claim에서 Gateway가 결정.

## Task 4. Databricks 사용자 Identity 및 OAuth/OBO

**개발 항목**

- 회사 사용자와 Databricks Identity 매핑·Provisioning 방식 선정
- Gateway에서 Databricks 사용자 OAuth/OBO Token 취득·전달 구현
- 현재 Gateway 공용 SP 호출과 사용자 Token 호출의 전환 정책 정의
- UC Row Filter, Column Mask, Dynamic View의 사용자 Identity 기반 정책 적용
- Token 캐시·만료·재시도·감사 로그·장애 처리 구현

## Task 5. Supervisor Agent Gateway 연동

**상태**  
상세 설계 완료, 단계 2~4 기본 실행 구조 구현 중

**목표**  
CUBE AI Agent 목록과 Gateway 자체 `/custom` 검증 화면에서 Supervisor Agent를 선택하고,
SSE 장기작업·중단·실행 이력을 포함한 대화를 수행.

**핵심 개발 항목**

- Supervisor endpoint 3개 이상 등록 가능한 Agent 리소스와 Admin 기능
- 공개 Agent ID 기반 Genie/Supervisor 통합 라우팅
- Databricks Responses SSE Adapter와 외부 event 정규화
- `long_task` continuation Orchestrator
- 연결·최초 이벤트·idle·전체 Run timeout
- `run_id` 기반 사용자 중단과 best-effort 취소 의미 정의
- Conversation·Run·Item/Event 이력 및 상태 전이
- 외부 고유 키 없이 `request_hash`로 진행 중 중복 실행 제한
- `/custom/supervisor-chat` 전용 검증 화면
- CUBE 외부 API 명세와 호출 예제

현재 Agent/Admin/DB 구조, 통합 Agent 목록, Supervisor streaming client, SSE 정규화,
DB Run 생성·상태 전이, 외부 SSE 응답, Run 상태·중단, 완료 Item 조회와 `long_task`
continuation, DB 실행 lease, `Last-Event-ID` Event 재생과 `/custom/supervisor-chat` 검증
화면까지 구현되었다. 남은 핵심 범위는 실제 endpoint 3개 이상의 통합 시험이다.

## 경계 및 주의사항

- `[user_id: ...]` 삽입과 Genie Instruction은 질의 정확도를 높이는 **초기 컨텍스트 전달 방식**임.
- 공용 Gateway SP로 Genie를 호출하는 동안 UC는 외부 `user_id`가 아닌 Gateway SP를 실행 주체로 인식함.
- 따라서 프롬프트만으로 사용자별 데이터 접근통제를 완성한 것으로 간주하지 않음.
- 초기에도 Gateway SP에는 필요한 Silver View만 최소 권한으로 허용하고, 테스트로 다른 사용자의 결과가 노출되지 않는지 검증해야 함.

## 권장 순서

```text
Task 1. Gateway user_id 삽입
            ↓
Task 2. Genie Instruction + Silver 매핑 검증
            ↓
Task 3. CUBE SSO/OAuth Token 검증
            ↓
Task 4. Databricks OAuth/OBO + 사용자별 UC 권한
```

Supervisor Agent 연동은 위 신원 고도화와 별도 트랙으로 진행할 수 있다. 1차는 현재
X-API-Key, `source_system`, `user_id` 경계를 재사용하고, 추후 Task 3·4가 구현되면 동일한
인증·사용자 권한 정책을 적용한다.
